# 配置文件的设计：六个必须想清楚的问题

规则集那部分我们已经工程化（单源双端、自动校验、冲突检测），但 `conf/` 还是手工艺。
配置文件是整个系统里**唯一不能远程更新**的部分——规则能远程改，节点能远程改，脚本能远程改，插件能一键装，只有配置文件必须手动改、手动传。

所以它应该被设计得比规则更保守。

---

## 一、配置文件必须最小化

每多一行，就多一行需要你手动同步的负担，而它是唯一没有版本控制兜底的那一层。

**放进配置的，只有两类东西：**

1. 不能远程化的：`[General]` 参数、`[Proxy Group]` 定义、`[Host]` 映射、`[Remote Proxy]` 订阅地址。
2. 必须最高优先级的覆盖：本地规则（理由见第二节）。

**不能放进配置的：**

- 大批量分流规则 → 放订阅规则，改一次全端同步；
- 去广告脚本与复写 → 放插件，能一键开关；
- 定时任务 → 放远程脚本，脚本挂了不影响主链路。

判断标准是一句话：**改它的时候，你需要重新导入配置吗？** 如果需要，它就该搬到远处。

---

## 二、`[Rule]` 段的顺序是假的

这一节推翻一个普遍误解。

Loon 的匹配规则是：

1. **先按来源分档**：`本地规则 > 插件规则 > 订阅规则`；
2. 同档内才按配置顺序，越靠前越优先。

所以把一条本地规则写在 `[Rule]` 段的最前面还是最后面，**结果一样**——本地规则整体压过所有订阅规则。

两个推论，都很重要：

- **逃生舱一定有效。** 想临时让某站直连，写在 `[Rule]` 任意位置都必然赢过订阅，包括装了去广告插件时插件的 REJECT。插件误杀就靠这里救。
- **本地规则无法「兜底」。** 你想让某条规则「晚于」订阅生效，做不到。想让某个域名被订阅里的宽泛规则放行后又被拦下，也做不到——本地永远先命中。

因此 `[Rule]` 段应该只有三块，顺序无所谓，但要分区写清楚：

```
[Rule]
# 1. 本地覆盖区（永远赢）
# 2. 订阅规则（按策略分文件，行序 = 轮次）
# 3. IP 层 + FINAL（只对裸 IP 生效，见第四节）
```

---

## 三、`FINAL` 是失效模式的选择，不是兜底

规则订阅是网络资源。它会加载失败：托管挂了、GitHub raw 被墙、文件 404。

**订阅加载失败的后果是：该组规则全部不生效。** 此时唯一还在工作的判断就是 `FINAL`。

所以 `FINAL` 不是「剩下的都走这里」，而是「**当我精心设计的一切都失效时，你希望它怎么坏**」。

| 选择 | 规则全挂时的表现 | 故障可见度 |
| --- | --- | --- |
| `FINAL,DIRECT` | 国内正常，墙外全不通 | **高**——立刻发现，立刻修 |
| `FINAL,PROXY` | 全部走代理，能上网但慢，且吃节点流量 | **低**——可能忍着用一周才发现 |
| `FINAL,兜底组`（fallback 逐级降级） | 按组内顺序退化，最终可能是 DIRECT | 中——取决于组内怎么排序 |

**本套选第三种**：`兜底组 = fallback, 自动优选, 故障转移, DIRECT`。

比裸写 `DIRECT` 好，因为漏网的境外站点还有机会走代理；比裸写 `PROXY` 好，因为节点全挂时还能退到直连而不是彻底断网。

但关键在于：**`GEOIP,CN,DIRECT` 必须写在本地 `[Rule]`，不能放在远程规则里。** 否则订阅一挂，国内流量就全绕道海外了——这才是我原来想说、但用错了理由的那个点。

**还有一层保底**：本地规则区里留 5～10 条最关键的代理域名（`google.com`、`github.com`、`openai.com` 这类），这样即使订阅全挂，你依然能用最核心的服务去排查问题。本地规则优先级最高，所以这几条永远有效。

## 四、`[General]` 里有因果链，抄参数不理解链条就会坏

这是配置文件里最容易出错、也最没人写清楚的部分。

### 链条 1：FakeIP 的边界（这一节我上一版写错了，已修正）

我原来的结论是「FakeIP → IP 层拿到假地址 → GEOIP 失效 → 只能靠域名白名单 → FINAL 必须 DIRECT」。**这个推理是错的。**

实际机制：

```
FakeIP（默认开）
  → 截获 App 自发的 DNS 请求，返回假地址
  → 请求回来时，Loon 把假 IP 映射回域名
  → 之后按域名走正常流程：真实 DNS 解析、匹配域名规则、再匹配 IP 规则
  → 所以 IP 层拿到的是真实 IP，GEOIP / IP-ASN 正常工作
```

`sni-sniffing = true` 再补一道：直接从 TLS 握手的 SNI 还原域名，连 FakeIP 这一层都不必依赖。

FakeIP 真正的作用是**让「自己解析 DNS 的 App」也能命中域名规则**，而不是要用假 IP 去做判定。

反过来验证：iKeLee 那套配置的 `FINAL` 指向代理组，国内流量全靠 `GEOIP,CN,DIRECT` 兜住。如果 GEOIP 在 FakeIP 下失效，他这套配置会让所有国内流量绕道海外——以它的使用规模不可能没被发现。

**所以：GEOIP 兜底是可靠的，前提是你信得过那个 GEOIP 库。** 这就引出 `geoip-url` / `ipasn-url`——它们决定判定准不准，详见 [peer-review.md](peer-review.md)。

### 链条 2：FakeIP 的副作用必须用 `real-ip` 补

```
FakeIP
  → 系统会缓存这些假地址
  → 关掉 Loon 后系统继续拿假地址发请求
  → Apple 推送、iCloud、App Store、局域网设备全部失联
  → 必须配 real-ip 豁免
```

最小可用集合：

```
real-ip = *.apple.com, *.icloud.com, *.mzstatic.com, *.push.apple.com, *.itunes.com
```

不配这条，你会以为是 Loon 的 bug，其实是自己在系统里留了脏缓存。

### 链条 3：`bypass-tun` 和 `skip-proxy` 是两条不同的路

流量进 Loon 有两条通道：**HTTP Proxy**（系统代理设置）和 **TUN**（虚拟网卡）。

- `skip-proxy` 管的是 HTTP Proxy 这条路；
- `bypass-tun` 管的是 TUN 这条路。

**只配一个，另一条路仍然会把局域网流量塞进 Loon。** 表现是打印机找不到、NAS 连不上、AirPlay 投屏失败、路由器管理页打不开——而且极难联想到是代理配置的问题。

两条都要配，且侧重不同：

| 参数 | 应包含 | 理由 |
| --- | --- | --- |
| `skip-proxy` | 内网段 + `*.local` + `localhost` + captive portal 域名 | HTTP Proxy 路径最容易误代理本地服务 |
| `bypass-tun` | 内网段 + `*.local` + 组播段 + 链路本地段 | TUN 会接管全部 IP 流量，范围要更宽 |

### 链条 4：`ipv6` 与节点的 `ip-mode`

```
ipv6 = false
  → 不做 AAAA 查询
  → 节点上写 ip-mode=prefer-v6 / v6-only 毫无意义
  → 但 ip-mode=v4-only 仍然有用：它管的是「解析节点域名」，不是「是否使用 IPv6」
```

这两个参数不在一个层级上，别混。

### 链条 5：`block-quic` 与 UDP 转发是矛盾的

```
block-quic=true   → 阻断 h3/QUIC
                  → 好处：HTTPS 流量能被 HTTP 引擎看到，复写规则生效
                  → 坏处：视频、游戏、部分 App 会回落到 TCP，体验下降

udp=true          → 允许节点转发 UDP
                  → 只有配合 block-quic=false 才真正能跑 QUIC
```

要转发 QUIC 就必须 `block-quic=false`；要抓 HTTPS 做复写就必须 `block-quic=true`。二选一，不能都要。

## 五、跨文件契约只有一处，但它会静默出错

整个系统里唯一需要跨文件对齐的东西是**策略组名**。

```
policy.json  →  "loon": "PROXY"
conf/loon.conf →  PROXY = select, DIRECT
out/loon/_include.conf → https://.../proxy.list,PROXY
```

三处必须完全一致。不一致的后果分两种：

- 策略组不存在 → 订阅规则加载报错，整组规则失效；
- 策略名拼错（大小写、全半角）→ **静默失效**，流量按 FINAL 走，你根本看不出来。

第二种最危险。所以这件事必须自动检查，不能靠人眼。

---

## 六、该检查的八件事

手写配置的错误几乎都能被静态检查出来。`check-conf.ps1` 做这些：

1. **段完整性**：`[General]` `[Proxy Group]` `[Rule]` 是否存在；
2. **策略名对齐**：`policy.json` 里的每个策略名，在 `[Proxy Group]` 里都有定义；
3. **规则引用的策略存在**：`[Rule]` 里每行的策略名都能解析到；
4. **`FINAL` 存在且在 `[Rule]` 最后**；
5. **占位符残留**：`EXAMPLE_HOST` 之类的没替换就上传了；
6. **FakeIP 相关**：配了 FakeIP 语义却没配 `real-ip`；
7. **路径覆盖**：`skip-proxy` 和 `bypass-tun` 是否都配了；
8. **订阅段错位**：订阅 URL 写进了 `[Proxy]`（应为 `[Remote Proxy]`）。

第 8 条是我自己在这份配置里犯过的错——写的时候很自然，错了以后节点一个都加载不出来，报错也不指向真正原因。

---

## 结论

配置文件应该满足三个性质：

- **最小**：只放不能远程化的东西；
- **显式**：每条参数背后的因果链写在注释里，不只写值；
- **可验证**：能被脚本检查，不依赖人眼。

这三条做到，配置就不再是「改一次怕一次」的东西。

跑一次检查：

```powershell
pwsh -File D:\Build\Loon\check-conf.ps1
```
