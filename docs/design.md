# 设计

这份文档回答一个问题：**为什么规则这样分、参数这样写。**
具体地址和语法见 [referencing.md](referencing.md)，协议选型见 [protocols.md](protocols.md)。

---

## 一、一条判定链

每条流量只回答两次问题，先定动作，再定出口要求。

```
拦不拦？
  ├─ 拦               → reject
  └─ 不拦
       ├─ 必须直连     → direct
       └─ 走代理
            ├─ 出口随便      → proxy
            ├─ 绑地区        → proxy-media
            ├─ 绑 IP         → proxy-ai
            └─ 要稳定        → proxy-social
```

落到文件就是这个顺序：

| 文件 | 动作 | 判定依据 | 误判后果 |
| --- | --- | --- | --- |
| `00-reject` | 拦 | 广告、埋点、归因 | 白屏、登录失败、上传中断，**最难排查** |
| `10-direct` | 直连 | 身份、资金、政务、长连接 | 风控、验证码收不到、消息延迟 |
| `20-proxy` | 代理·通用 | 搜索、代码托管、包管理、协作 | 打不开 |
| `30-proxy-media` | 代理·地区 | 影视、音乐 | 换区失败、起播慢 |
| `40-proxy-ai` | 代理·IP | 模型服务 | 判定为代理，拒绝服务 |
| `50-proxy-social` | 代理·稳定 | 通讯、社区 | 长连接重连、消息延迟 |
| `90-direct-ip` | 直连 | IP 层兜底 | 见第六节 |

`reject` 排第一是因为它的故障最隐蔽。出问题时先关这一组，再看还坏不坏，这一步能省掉大半排查时间。

**为什么不用「按主题」分**（把所有 CDN 放一起、所有游戏放一起）：那样每个文件里混着不同动作，出问题你没法判断该关哪一组。分成动作层之后，每一层对应一种明确的故障表现。

## 二、iOS 上没有「按 App 分流」

这是整套设计里最容易被误解的地方。

Loon 文档原文：进程规则按可执行文件名称或路径匹配，**仅在 macOS 上生效，iOS 和 tvOS 忽略进程规则**；含进程条件的整条逻辑规则也会被忽略。

原因在系统层。iOS 的 Network Extension 只能看到 socket 元数据：目标地址、端口、协议、经 SNI 或 DNS 还原出的域名。看不到发起连接的是哪个进程。沙盒加网络扩展的架构决定了这条路走不通。

所以 `PROCESS-NAME,Telegram,PROXY` 这类写法在 iPhone 上是死规则。网上大量规则集里有它们，抄过来等于没写。

`USER-AGENT` 能补一点，但覆盖面很窄：UA 规则只对经过 HTTP 引擎的请求有效，HTTPS 要先 MitM 解密。为了分流去解密全部流量，代价和收益不成比例。

**所以按「用途」分，不按 App 分。**

用途由你的使用意图决定，App 只是载体。按 App 分组会腐烂：厂商换 CDN、换域名、白名单永远滞后。用途不会。

代价是同一个 App 里不同功能可能落在不同用途。微信的视频号是流媒体，聊天是即时通讯，按用途分拆不开。但按 App 分本来也拆不开，两边是同等的限制。

## 三、出口要求决定策略组类型

| 用途 | 关键指标 | 典型失败 | 组类型 |
| --- | --- | --- | --- |
| 通用 | 综合 | 打不开 | `url-test` + `fallback` |
| 流媒体 | 地区匹配、带宽 | 换区失败 | `select`，固定地区 |
| AI | IP 纯净度 | 被判定为代理 | `select`，固定节点 |
| 社交 | 连通稳定性 | 长连接重连 | 允许自动切换 |

**AI 那一条最反直觉。** 其他场景都在追求自动切换，唯独 AI 相反：OpenAI、Claude 这类服务按出口 IP 判风控，`url-test` 会在节点间按延迟自动跳，换 IP 的代价是触发验证甚至封号，远大于省下几十毫秒。

流媒体同理，但原因是地区：自动优选可能把你跳到日本，而你的 Netflix 账号是美区。

所以配置里 `流媒体` 和 `AI` 只挂在地区筛选集合上，不挂 `PROXY`，因为 `PROXY` 里有 `url-test`。只有 `社交` 可以挂。

**自动切换适合通用场合，不适合有状态或地区绑定的场景。** 这条区分比分组方式本身更重要。

## 四、FINAL 是失效模式的选择

规则订阅是网络资源。托管挂了、raw 被墙、文件 404，它就会加载失败。

**订阅加载失败的后果是那组规则全部不生效。** 此时唯一还在工作的判断就是 `FINAL`。

| 选择 | 规则全挂时的表现 | 故障可见度 |
| --- | --- | --- |
| `FINAL,DIRECT` | 国内正常，墙外全不通 | 高，立刻发现 |
| `FINAL,PROXY` | 全部走代理，能上网但慢 | 低，可能忍一周才发现 |
| `FINAL,兜底组` | 按组内顺序逐级降级 | 中 |

本套用第三种：`兜底组 = fallback, 自动优选, 故障转移, DIRECT`。比裸写 `DIRECT` 多两级，比裸写 `PROXY` 在节点全挂时还能退到直连。

关键配套：**`GEOIP,CN,DIRECT` 必须写在本地 `[Rule]` 段，不能放远程规则。** 放远程的话订阅一挂，国内流量就全绕道海外，这种失效极其隐蔽。

另外留了几条核心域名的本地保底（google、github、openai、telegram），订阅全挂时还能上网去修。

## 五、规则来源优先级

Loon 的匹配是**先按来源分档，再按位置排序**：

```
本地规则 > 插件规则 > 订阅规则
```

两个推论，都很实用：

**逃生舱一定有效。** 本地规则写在 `[Rule]` 第几行都赢过订阅，包括装了去广告插件时插件的 REJECT。插件误杀就靠这里救。

**本地规则无法兜底。** 想让某条规则「晚于」订阅生效，做不到。本地永远先命中。

## 六、`[General]` 里的因果链

抄参数不理解链条，就会写出互相打架的配置。

### FakeIP 的边界

```
FakeIP 开
  → 截获 App 自发的 DNS 请求，返回假地址
  → 请求回来时把假 IP 映射回域名
  → 之后按域名走正常流程：真实 DNS 解析、匹配域名规则、再匹配 IP 规则
  → IP 层拿到的是真实 IP，GEOIP / IP-ASN 正常工作
```

`sni-sniffing=true` 再补一道：直接从 TLS 握手的 SNI 还原域名。

FakeIP 的作用是让「自己解析 DNS 的 App」也能命中域名规则，不是拿假 IP 去做判定。

但它有副作用必须补：

```
FakeIP → 系统缓存假地址 → 关掉 Loon 后系统继续拿假 IP 发请求
       → Apple 推送、iCloud、App Store 全部失联
       → 必须配 real-ip 豁免
```

最小集合：`*.apple.com, *.icloud.com, *.mzstatic.com, *.push.apple.com`。

### 两条路径都要覆盖

流量进 Loon 有两条通道：HTTP Proxy 和 TUN。`skip-proxy` 管前者，`bypass-tun` 管后者。

只配一个，另一条仍然会把局域网流量塞进 Loon。表现是打印机找不到、NAS 连不上、AirPlay 投屏失败，而且极难联想到是代理配置。

### block-quic 与 udp 矛盾

`block-quic=true` 让 HTTPS 能被 HTTP 引擎看到（复写规则才生效），但视频、游戏、部分 App 会回落到 TCP。
`udp=true` 配合 `block-quic=false` 才真正能转发 QUIC。

二选一，不能都要。

### 未经验证的键会让整份配置消失

Loon 遇到 `[General]` 里不认识的键，不一定忽略，可能整份拒收。症状是**导入后配置空白，客户端不报错**，只留一份空配置，看起来像网络问题。

本套配置里曾有六个键来自参考配置而不是官方文档：

```
ip-mode / sni-sniffing / dns-reject-mode
domain-reject-mode / udp-fallback-mode / disconnect-on-policy-change
```

它们在 `conf/loon.conf` 里保留为注释。要加回时一次只加一个，导入后确认配置非空。同时加多个，出问题就不知道是哪一个。

`check-conf.ps1` 会拦这一条：`[General]` 里出现白名单外的键就警告。白名单只收官方 `[General]` 文档页里列出的键。

**这条约束比它看起来重要。** 一个键写错不会给你任何提示，只会让整份配置消失，然后你会去怀疑网络、怀疑 CDN、怀疑导入方式，唯独不会怀疑那个键。

## 七、节点筛选

`[Remote Filter]` 用正则从订阅里筛节点集合，策略组引用集合而不是节点名。好处是机场改名加减节点不用改配置。

**真正难的不是识别，是排除。** 订阅里混着大量不是节点的条目：

```
剩余流量：123.45 GB
套餐到期：2026-12-31
官网地址：xxx.com
邀请好友得返利
```

这些被筛进 `url-test` 会让测速失败，拖垮整组。所以排除词的权重高于识别词：

```
过期|到期|剩余|官网|订阅|流量|套餐|群|邀请|返利|客服|通知
超时|失联|回国|校园|重置|续费|试用|官方|地址|网址|版本|备用
```

识别侧要同时覆盖 emoji、中文、英文缩写、城市名四种线索，因为同一个地区不同机场写法完全不同：`🇭🇰 香港 01`、`HK-01`、`Hong Kong 01`。

**不要专门筛「游戏节点」。** 机场标着游戏专用的绝大多数是营销包装，实际延迟未必低。延迟该用 `url-test` 实测，不该信名字。

## 八、修正记录

设计过程中有三条判断被推翻，留档以免重犯。

**一、FakeIP 会让 GEOIP 失效。**
当时的推理是「FakeIP 返回假 IP → IP 层判不准 → 只能靠域名白名单 → FINAL 必须 DIRECT」。错在第一步：Loon 会把假 IP 映射回域名再真实解析，GEOIP 有效。反证是一份成熟配置用 `FINAL` 指向代理组，靠 `GEOIP,CN,DIRECT` 兜国内流量，如果 GEOIP 失效那套配置会让所有国内流量绕道海外。

**二、`ssid-trigger` 只能切全局模式，多环境得靠多份配置。**
错。`ssid` **类型的策略组**可以按 Wi-Fi 指定任意策略，粒度到单个组。`ssid-trigger` 是全局开关，`ssid` 组是逐组开关。

**三、订阅规则语法是 `URL,POLICY`。**
不全。实际支持 `policy=` / `tag=` / `enabled=`。少了 `tag` 就没法在界面里按组开关，排障时很吃亏。

**四、`[General]` 里写点没验证过的键没关系。**
错。Loon 可能整份拒收，症状是导入后空白且不报错。六个从参考配置带来的键让配置一直导不进去，逐个注释掉才恢复。**这是最贵的一次误判**，因为它伪装成网络故障，把排查引向错误的方向。

四条的共同点：都是从文档片段或经验推出的结论，没经过实测。**推断和验证之间要留一道手续。**
