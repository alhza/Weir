# 节点筛选与分流策略

两件事：按什么分组节点，按什么决定流量去哪。

第二件事有个前提必须先说清楚，否则整节设计都是空中楼阁。

---

## 一、iOS 上没有「按 App 分流」

Loon 文档原文：进程规则按可执行文件名称或路径匹配，**仅在 macOS 上生效，iOS 和 tvOS 忽略进程规则**；包含进程条件的整条逻辑规则也会被忽略。

原因在系统层：iOS 的 Network Extension 拿到的只有 socket 元数据，目标地址、端口、协议、域名（经 SNI 或 DNS 还原），拿不到发起连接的是哪个进程。沙盒加网络扩展的架构决定了这条路走不通。

所以 `PROCESS-NAME,Telegram,PROXY` 这类写法在 iPhone 上是死规则。网上大量规则集里有它们，抄过来等于没写。

### 那能不能用 USER-AGENT 补

能，但覆盖面很窄。UA 规则只对经过 HTTP 引擎的请求有效，而 HTTPS 要先 MitM 解密。代价是：装证书、处理证书固定、部分 App 直接拒绝连接。为了分流去解密全部流量，收益和风险不成比例。

结论：**iOS 上做不了真正意义上的按 App 分流。**

---

## 二、所以改成按「用途」分

既然按 App 不可行，退一步看真正的需求是什么。

你要的不是「让 Telegram 走代理」，是「聊天别延迟、看片别卡、AI 别封 IP」。目标的粒度其实是**用途**，App 只是用途的载体。

按用途分组有三个好处：

**稳定。** 用途由你的使用意图决定，不会因为 App 改名换域名而失效。按 App 分组的话，厂商换一次 CDN 你的规则就废一条。

**可测。** 流媒体要的是解锁地区，AI 要的是干净 IP，游戏要的是低延迟。这些指标能直接对应到选哪组节点。

**不腐烂。** App 的白名单永远滞后于厂商的发布节奏。用途不会。

代价是：同一个 App 里不同功能可能落在不同用途。比如微信里的视频号是流媒体，聊天是即时通讯。按用途分就没法拆开。

这个代价可以接受，因为按 App 分本来也拆不开。

---

## 三、三类用途的节点需求不一样

| 用途 | 关键指标 | 典型失败 | 选点策略 |
| --- | --- | --- | --- |
| 流媒体 | 地区匹配、带宽 | 换区失败、起播慢 | 固定地区，优先大带宽，不要 url-test 乱跳 |
| AI | IP 纯净度 | 被判定为代理，拒绝服务 | 固定节点，**绝不能频繁切换** |
| 社交 / 通讯 | 连通稳定性、UDP | 长连接反复重连、消息延迟 | 自动优选，允许切换 |
| 通用代理 | 综合 | 打不开 | 自动优选 + 故障转移 |

**AI 那一条最反直觉**：url-test 会在节点间按延迟自动切换，而 OpenAI / Claude 这类服务会因为你频繁换出口 IP 触发风控，表现为「突然要重新验证」甚至封号。所以 AI 组的类型应该是 `select` 并固定一个节点，正相反于其他组追求自动。

**流媒体**同理，但原因是地区：自动优选可能把你跳到日本，而你的 Netflix 账号是美区。

所以自动切换适合通用场合，不适合有状态或地区绑定的场景。这条区分比分组方式本身更重要。

---

## 四、节点筛选怎么才不脆

`[Remote Filter]` 用正则从订阅里筛节点，策略组引用筛出来的集合。这层的健壮性完全取决于机场的命名。

### 命名混乱的实际情况

同一个地区，不同机场会写成：

```
🇭🇰 香港 01
香港节点 A
HK-01
Hong Kong 01
香港 01 | 1x
🇭🇰HK-01-IEPL
```

正则要同时覆盖 emoji、中文、英文缩写、城市名四种线索。

### 干扰项比识别项更重要

订阅里混着大量**不是节点**的条目：

```
剩余流量：123.45 GB
套餐到期：2026-12-31
官网地址：xxx.com
客服频道：@xxx
邀请好友得返利
节点重置时间：每月 1 号
```

这些条目如果被筛进 url-test，测速会失败，还可能把整组拖成不可用。所以正则里**排除部分的权重高于匹配部分**。

排除词是这套方案的核心资产：

```
过期|到期|剩余|官网|订阅|流量|套餐|群|邀请|返利|客服|通知
超时|失联|回国|校园|重置|续费|试用|官方|地址|网址|版本|备用
```

### 一个反直觉的判断

不要专门筛「游戏节点」。

机场标着「游戏专用」的节点，绝大多数只是营销包装，实际延迟未必低于普通节点。延迟该用 `url-test` 实测，不该信标签。真要做游戏分流，靠的是 UDP 转发能力和实测延迟，不是名字里有没有「游戏」两个字。

## 五、落地结构

规则按用途分层，策略组按用途定义，节点按地区筛选。

```
[Remote Filter]        正则筛出  全部 / 香港 / 日本 / 美国 / 新加坡
        ↓
[Proxy Group]  地区组  手动 select + 自动 url-test + 故障 fallback
        ↓
[Proxy Group]  用途组  流媒体 / AI / 社交 / 通用，各自挑地区组做成员
        ↓
[Remote Rule]  规则    按用途分文件，指向用途组
```

规则文件与用途的对应：

| 文件 | 策略 | 内容 |
| --- | --- | --- |
| `00-reject` | REJECT | 广告与埋点 |
| `10-direct-local` | DIRECT | 身份、资金、政务、长连接 |
| `20-proxy-core` | PROXY | 基础设施：搜索、代码托管、包管理、协作工具 |
| `30-media` | 流媒体 | 影视与音乐 |
| `40-ai` | AI | 需要固定 IP 的模型服务 |
| `50-social` | 社交 | 通讯与社区 |
| `90-ip` | DIRECT | IP 层兜底 |

一个域名只能出现在一个文件里。构建时会检查这一点：同一条规则落在两个策略里，命中结果就取决于文件顺序，属于必须修掉的硬冲突。

## 六、什么时候该回来的看的地方

分流不准时，先看请求记录命中了哪条规则，再判断属于哪种情况：

- **命中了但策略不对**：规则文件写错层了，挪文件
- **没命中，走了 FINAL**：域名没被收录，补规则
- **命中了但节点不通**：节点问题，不是规则问题

这三种的处理路径完全不同，先分清再动手，比直接改规则快。
